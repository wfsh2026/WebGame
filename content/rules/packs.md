# 内容包、清单与发布

## 权限

| 层级 | 范围 | 合入要求 |
| --- | --- | --- |
| 配置创作 | 地图、怪物属性、技能组合、事件、表现资源 | 限定在指定内容包，遵守已实现的配置格式 |
| 机制扩展 | 新技能效果、怪物行为、玩法规则 | 明确扩展接口，经核心维护者审核后统一部署 |
| 核心系统 | 网络、账号、背包、货币、结算、公共框架 | 仅指定维护者在明确授权任务中修改 |

首期不支持上传并直接执行任意 TypeScript/JavaScript。接口、类型和白名单不是运行时安全沙箱。

## 格式与引用

```text
content/packs/<pack-id>/
├─ manifest.json
├─ hearts/
├─ weapons/
├─ skills/
├─ supports/
├─ maps/
├─ characters/
├─ enemies/
├─ events/
└─ assets/
```

按需建立子目录，不强制创建空文件。当前不建立带假参数的可加载示例秘境。

### 独立内容与清单职责

- 心法、武器、技能和辅助分别存放在 `hearts/`、`weapons/`、`skills/`、`supports/`，每份内容具有独立 ID，通过 ID 建立业务引用，不复制整份属性作为引用。
- ID 沿用 `<pack-id>:<kind>/<name>`，对应类型为 `heart`、`weapon`、`skill`、`support`。精确字段及加载索引由内容格式模块统一实现。
- `manifest.json` 保存包信息、兼容版本、入口、编排及内容引用，不再承载所有具体心法、武器、技能和辅助属性。
- 清单可以登记包内文件路径供加载器定位；内容之间使用 ID 引用，不能用跨包文件路径绕过公开依赖。
- 未发布内容位于 `development/features/<feature-id>/content/`，使用相同的包内分类结构；转正时保持内容 ID 稳定，不将开发目录当作正式依赖。
- 当前首包的这些配置仍内嵌于清单，Schema 与加载器也采用内嵌结构。以上是已确认的目标规范，迁移需要同步修改内容、Schema、引用解析与消费端，不能只拆文件便宣称可加载。本次不执行配置迁移。

清单格式由 `packages/content-schema` 统一实现，至少包含以下信息；字段名和具体 Schema 在实现时统一落地，创作者不能自行约定另一套格式。

| 信息 | 约束 |
| --- | --- |
| ID、名称、版本 | ID 唯一稳定；内容版本和配置格式版本分别管理 |
| 核心兼容版本 | 不兼容时拒绝开启房间 |
| 入口地图、资源清单 | 使用包内路径，不允许路径越界或任意远程 URL |
| 内容依赖 | 只引用已公开的公共内容及固定兼容版本 |
| 人数、时长 | 在平台允许范围内，由玩法方案确定 |
| 开始、结束条件 | 使用已实现的条件类型 |
| 小秘境编排 | 在平台允许范围内声明各轮内容，不能替换核心主循环 |
| 携带、成长、死亡规则 | 使用统一规则模板 |
| 积分获取规则 | 由各秘境设计，不统一限制得分行为、来源和分值；正式计算由服务器执行 |
| 奖励档位 | 遵守公共资产与结算规则，使用批准的奖励模板，不由积分配置直接写永久资产 |
| 异常结束策略 | 引用平台统一策略，不自行发放补偿 |

示例内容 ID：`ruins-survival:skill/fireball`。ID 不因显示名称变化而改变，移除已有 ID 时需要处理版本兼容。

## 生命周期约定

遵守 [游戏核心主循环](../../docs/gameplay/core-loop.md)。完整秘境、小秘境和秘境大厅是不同概念，不能用一次“进行 → 结算 → 销毁”替代整个多轮流程。

内容提供当前轮玩法和完成条件，由核心流程管理等待、统一传送、单轮结算、返回成长、下一轮和最终结算。单轮结束不销毁整次会话；单轮结算后冻结该轮成果，不阻止后续轮次按规则计分。新版本仅影响新开秘境，运行中的会话使用锁定版本。

## 发布

内容配置仅能引用已部署机制。资源、配置和机制版本应成套发布，客户端与服务器不兼容时拒绝开局。

首版已有内容清单与受限地图的 Zod 运行时校验，房间启动会执行；通用发布、资源导出及独立内容校验 CLI 尚未实现。已有首包不代表所有表内类型或扩展接口都可用。
