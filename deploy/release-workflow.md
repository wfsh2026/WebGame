# 开发、转正与发布流程

## 四个层次

| 层次 | 位置与职责 |
| --- | --- |
| 开发验证区 | `development/`，孵化未发布功能 |
| 正式源码 | `apps/`、`packages/`、`content/`，纳入产品不等于上线 |
| 发布产物 | 本地 `releases/<release-id>/`，不手工编辑、不提交 Git |
| 玩家网站 | 已授权正式环境中的部署版本 |

浏览器资源、服务端程序与内容数据分别打包；服务器代码、密钥及隐藏数据不得进入浏览器产物。本地产物目录不自动对应服务器路径。

## 固定发布顺序

1. 开发完成后交付修改说明、使用方式及已知限制，保持待构建状态。只有用户明确要求才构建测试产物；只要求本地构建不自动部署，已明确授权的范围不重复确认。
2. 用户要求更新测试网页时，整合完整测试功能并生成带版本标识的产物，同步必要的 API、房间、内容及数据库迁移。修复后重新构建和部署也按用户明确要求执行。
3. 实际部署后维护 [测试更新列表](test-updates.md)，提供测试链接、版本、功能入口及限制，由用户体验确认。构建成功或服务可访问不能替代用户确认；修改后的功能需重新确认。
4. 正式发布前按下节列出全部待发布内容，让用户选择范围。测试确认不等于发布授权，旧版本确认不覆盖新增变化。
5. 用户确认所选内容并授权发布后，必要时将实现迁入正式模块，修正引用并去除重复代码。按选定范围与锁定依赖生成正式产物，保留已有正式功能，排除未选代码、服务、配置、资源及迁移，不能仅隐藏按钮。
6. 按 [部署操作](operations.md)切换目标版本；数据库变更先备份，房间切换先限制新入场，确认活动对局及等待房间均为空。保留正式账号资产，不导入测试数据。
7. 核对版本、资源及服务可访问状态，恢复入口，完成临时内容清理。回填正式版本、实际功能范围、数据库变更、备份及回退依据，并提供正式链接。

资源构建、Prisma Client 生成、迁移及可访问状态核对属于获准发布所需操作，不增加额外编译检查、功能测试或验收脚本。测试与正式版本对应关系保留在发布记录中；归档期限、自动化工具及正式域名仍待确定。

## 测试更新记录与正式发布选择

- 每次实际更新测试网页，记录新增、调整、修复、美术及配置变化；本地完成不能记为已进入测试。
- 按可选择的功能设置稳定编号，维护效果、最近测试版本及日期、用户确认、依赖、限制、选择状态和正式版本。同一功能修复更新当前条目并追加历史。
- 正式发布前列出所有尚未发布的测试内容，包括待体验、已确认、暂缓及已上线功能的新修改；不能只列当前对话或最近更新。已与正式一致的内容单独概括，空表不能替代实际版本核对。
- 展示独立发布能力与依赖。所选功能需要未选内容时，整理拆分方案或必须合并的依赖，由用户决定，不静默扩大范围。拆分产生行为变化时，按授权更新同一测试网页，重新取得对应确认。
- 未选内容留在测试版本。发布成功后才标记已发布；失败、回退如实记录，后续修改重新列为待发布。

## 服务器版本保留与临时内容清理

- 服务器仅保留本项目一个正式版本和一个完整测试版本，包含目录、静态资源、API、房间及版本专用容器；各环境所有模块归入当前版本，不长期挂载旧目录。
- 上传、解压、构建和切换暂存仅在本次部署期间存在，不开放额外入口。成功后清理旧版本，失败恢复后清理失败候选。
- 清理失效目录、压缩包、临时脚本与日志、调试导出、缓存、旧静态资源及闲置版本容器和镜像；保留当前依赖及共享运行时，不按名称猜测用途或全局清理 Docker。
- 删除前核对真实路径、软链接、容器挂载和资源引用；使用中的内容先迁移或解除引用，房间切换遵守活动对局处理要求。旧页面需要刷新时提示用户，不长期保留旧哈希资源。
- 账号资产、数据卷、当前凭据、必要业务日志、数据库恢复备份及受保护旧站不属于临时内容。
- 回退产物在本地或服务器外归档，回退时重新部署到对应唯一入口；服务器不保留第三个版本。历史记录中的“旧版已保留”不构成继续保留的依据。
- 发布记录注明最终两个版本、清理范围和残留原因；有临时残留不能宣称清理完成。

## 环境隔离要求

- 测试与正式的入口、API、房间、数据库和凭据隔离；部署测试内容不切换正式软链接、修改正式环境或重启正式服务。
- 测试账号资产不迁入正式。通过访问限制与构建范围隔离，不能仅隐藏按钮或链接。
- 原首页、`/mhxy/` 及其他业务保持原有保护范围；操作遵守 [部署说明](operations.md)。
