# 结算与奖励发放规范

房间生成本局成果，API 服务负责核对及永久资产发放。适用于两端结算模块。

当前首版已实现可信提交、最终奖励事务及幂等。`RoundRecord` 目前按“场次 + 轮次”聚合存储个人成果数组，未实现独立的每人每轮明细表；最终 `Participant`、`AssetLedger` 按场次与玩家约束。聚合轮次记录尚未满足下文确认的独立个人结果保存要求，需在后续实现任务中补齐，不能将文档确认视为代码已经完成。具体实例见 [当前实现](../../../docs/implementation/limitations.md)。

## 个人独立结算（正式要求）

- 小秘境与最终结算均以每个玩家为独立结算对象，计算并保存该玩家自己的成果、奖励和结算状态。
- 每位玩家具有可独立查询、追踪及防重复处理的个人结算记录；不能仅用一条全队汇总或轮次内数组替代个人结果记录。
- 小秘境个人记录关联完整秘境场次、轮次及玩家；最终个人记录关联完整秘境场次及玩家。
- 共享目标或队伍成果可以参与计算，但最终结果必须归属具体玩家，不能用队伍总奖励替代个人结果。
- 独立结算不表示每个玩家自行决定阶段推进、独自进入下一轮或自行发奖，也不要求结算操作必须串行执行。
- 最终结算完成后弹出本局个人收益界面，玩家主动关闭后独立返回游戏大厅。发奖、处罚和保存结果不依赖玩家关闭，也不能因关闭或重复打开界面再次处理资产。

## 两层结算

2026-11-12 第一秘境新增已确认规则：保险箱中的怪物掉落在正常全队失败后的最终结算进入大厅库存，保留掉落等级；本局不可使用，不能与局内临时物品混淆。发放与最终资产结算同事务，按场次与掉落编号去重。具体见 [怪物掉落规则](../../../docs/gameplay/monster-loot.md)。这项明确授权优先于下文旧的待确认描述。

最终物品奖励可以包含有等级的技能石、装备及心法；这不意味着已批准失败后发放永久物品。失败后新生成结算物品能否进入大厅仓库仍待确认，不得通过重命名来源绕过失败损失。局内物品、临时成长与最终发放分别记录，遵守 [构筑成长规范](../../../docs/gameplay/build-growth.md)。

先读 [游戏核心主循环](../../../docs/gameplay/core-loop.md)。每轮小秘境结算和整次秘境最终结算必须区分，不能将每轮结束都视为整次结束。

小秘境奖励用途及带出规则尚未确定，不默认每轮向永久钱包发奖。涉及局内成长的结果由客户端运行、房间协调同步，涉及永久资产的发放由本服务处理。以下发放流程适用于永久资产结算。

## 发放流程

1. 房间结束后冻结成果，生成包含场次、玩家、内容版本、规则版本和有效行为摘要的结算数据。
2. 房间通过服务器间受信通道提交，大厅服务验证提交方与对应场次资格。
3. 大厅服务根据锁定规则计算或核对奖励，拒绝未经授权的金额和物品。
4. 在数据库事务内记录结算、修改资产、写入资产流水。
5. 返回可重复查询的结果，客户端刷新资产与结算展示。

最终结算以“完整秘境场次 ID + 玩家 ID”建立唯一约束。小秘境结算以“完整秘境场次 ID + 轮次标识 + 玩家 ID”建立独立唯一约束，轮次标识不能仅使用地图 ID，因为相同内容可能被重复编排。结算类型需要明确区分，重试返回已有结果或安全恢复处理，不能重复发放。

服务器间提交权限、幂等约束和数据库事务缺一不可。不能仅以客户端持有场次 ID 或提交积分为理由发奖。

## 异常与可信数据

正常死亡或全队失败不是服务器异常，按 [死亡与失败惩罚](../../../docs/gameplay/failure-penalties.md)处理。按玩家保存物品损失、装备判定及经验扣除结果，重试不重新抽取掉落或重复扣除经验；具体尚待确定的数值不能由实现者自行填写。

房间崩溃可能发生在提交前后，必须区分“未提交”“待处理”“已完成”等结算状态。不能仅根据请求超时判定失败并重复发奖。

具体重试、恢复与补偿政策在实现相关功能时确定。当前规范只定义约束，没有实现消息队列、持久化恢复或补偿系统。

浏览器包内的代码和配置均视为公开。密钥只保存在服务器环境中，示例配置使用占位值。用户凭证、账号隐私和连接字符串不得写入日志或内容包。
